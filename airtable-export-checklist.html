The complete Airtable export checklist: records, schema, attachments, views, automations

Most "exports" of an Airtable base are a few CSV downloads — and most people who later try to rebuild the base discover what a CSV leaves behind: attachments reduced to links that expire within hours, views and automations gone entirely. Whether you are migrating to another tool, archiving a finished project or building an exit plan, a complete export has five pieces. Here is each one, the native way to get it, the gap to watch, and where a tool helps.

1. Records

Native way: download a CSV from each view, or pull every field through the API. The gap: a CSV contains exactly what the view shows — hide a field and it silently drops out of your export — and it carries no record IDs, which are the only reliable way to reconnect linked records after a move. Export from a view with every field visible, or use the API and keep the IDs. One table with several views still needs only one full export; do not archive five partial CSVs of the same data.

2. Schema

Native way: the API's "Get base schema" endpoint returns tables, fields (with types and options) and views as JSON; without API access, document the schema by hand. The gap: the schema describes structure, not behavior — it will not tell a future you why a formula exists or what a rollup feeds. Add one line of intent per non-obvious field while the knowledge is still in the building. This is also the piece most backups skip entirely; the backup guide covers why that hurts at restore time.

3. Attachments

Native way: there isn't one for the files themselves. The URLs in a CSV or API response expire within hours, so an "export" that only saves the spreadsheet is a countdown, not an archive. The gap: the actual files must be downloaded while the links are fresh, ideally with names and folders that mean something outside Airtable. A script or a bulk downloader does this in one run per table; organizing the tree is covered in the folders guide.

4. Views

Native way: the API schema lists view names and types, and that is where native export stops. The gap: filter conditions, sorts, groupings and hidden-field choices are not exposed for export by any route we know of — no tool can faithfully recreate your views in another system. The practical move is documentation: for each view that matters, record its filter, sort and grouping in a note or screenshot next to the export. It takes minutes per view and is the difference between rebuilding in an afternoon and archaeology.

5. Automations

Native way: none. Automations cannot be exported or imported. The gap: triggers, conditions and actions live only inside the base. Document each automation — trigger, condition, what it changes or sends — and screenshot the configuration. If you are migrating, expect to rebuild them natively in the destination or in a tool like Make or n8n; the document you write here is the specification for that rebuild. Interfaces and extensions deserve the same treatment: a screenshot and a paragraph beat a surprise later.

Putting it together: a realistic export run

In order: (1) snapshot the schema via the API and save it with the export; (2) export records per table with IDs; (3) download the attachment files themselves, renamed and foldered; (4) walk the views and automations and write the one-page document for each; (5) spot-check the result by opening files from a different machine and confirming the counts match. Expect the attachments step to be the long one — everything else is minutes.
